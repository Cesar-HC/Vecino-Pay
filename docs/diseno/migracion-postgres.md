# Migración a PostgreSQL 17 local, sin Docker

Decisión del usuario (2026-11-09, `docs/escalaciones.md`, opción B): no se discute, se diseña. Se mantienen las 11 tablas, los nombres de tabla y de columna, las cifras al céntimo, las reglas del informe y los RF. Cambia el motor, la forma de ejecutar y el código que dependía de T-SQL.

## 1. Resumen del diseño

1. El esquema se reescribe en PostgreSQL 17 con los mismos nombres y las mismas restricciones. Las dos columnas con otro tipo que el informe (`fecha_hora` y `detalle`) y los 3 triggers se traducen uno a uno (sección 3).
2. Dos roles sin privilegio de superusuario: `vecinopay_owner` (dueño de las bases y de los objetos, con `CREATEDB`) y `vecinopay_app` (la API, sin DELETE y sin DDL). El superusuario `postgres` solo se usa una vez, para crear los roles.
3. Los bloqueos de T-SQL (`UPDLOCK, ROWLOCK`) pasan a `SELECT ... FOR NO KEY UPDATE`, en el mismo orden (tienda, cliente, listado). No se usa `FOR UPDATE` ni advisory locks (sección 6.2).
4. Todo corre con Node y `psql`: scripts en `scripts/` (sin dependencias nuevas), API en 3000, web en 8080 con `vite preview` y proxy a `/api`. Integración usa la base `vecinopay_test` y e2e la base `vecinopay_e2e`, ambas desechables en el mismo servidor.
5. La equivalencia se demuestra con las mismas pruebas, sin cambiar un solo valor esperado: 52 chequeos y 7 pruebas negativas de `db:verificar`, jest unitario e integración, y las 23 pruebas de Playwright.

Desviación declarada frente al informe (ya aceptada por el usuario; el Word lo corrige el grupo): sección 8 dice SQL Server en 4428 y 5109, y las figuras 48 y 49 del Anexo 4 son el script T-SQL. También cambian los tipos `DATETIME2` (Tablas 27 y 33, líneas 1475, 1495, 4657, 4901) y `NVARCHAR(MAX)` (Tabla 33, línea 4909); también hay mención en las líneas 375 y 444 del índice de contenido. El auditor debe marcar "CONFORME con desviación declarada" en esos puntos y comprobar que no hay otra diferencia.

## 2. Convenciones del esquema en PostgreSQL

- Una sola base por entorno, esquema `public` (en PostgreSQL 15 o superior `PUBLIC` ya no puede crear ahí; se revoca de forma explícita igualmente). Los nombres no llevan prefijo `dbo.`.
- Identificadores sin comillas, por lo tanto en minúscula. Las restricciones conservan su nombre en minúscula: `pk_usuario`, `uq_usuario_username`, `ck_compra_modalidad`, `fk_compra_cliente`. Prisma no usa estos nombres en tiempo de ejecución; `map:` se actualiza para que coincidan.
- Idempotencia como hoy: `CREATE TABLE IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, `CREATE OR REPLACE TRIGGER` (PostgreSQL 14 o superior). Nunca `DROP`.
- Cada archivo SQL: UTF-8 sin BOM, fin de línea LF (`.gitattributes` ya lo fuerza) y `psql` con `PGCLIENTENCODING=UTF8` (equivale al `-f 65001` de `sqlcmd`). Ninguna prueba debe depender de la codificación de la consola de Windows.
- Base creada con `ENCODING 'UTF8'`, `TEMPLATE template0`, `LOCALE_PROVIDER icu`, `ICU_LOCALE 'es-PE'` (orden y mayúsculas parecidos a `Modern_Spanish_CI_AS`). Si la instalación no trae ICU, `scripts/db.mjs` cae a la configuración por defecto y `db:estado` lo avisa (decisión 6 de la sección 13).

## 3. Mapeo de tipos y construcciones (punto 1)

| T-SQL actual | PostgreSQL | Prisma | Nota |
|---|---|---|---|
| `BIGINT IDENTITY(1,1)` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BigInt @id @default(autoincrement())` | No requiere GRANT sobre la secuencia. Los huecos tras un rollback ocurren igual que en SQL Server |
| `VARCHAR(n)` | `VARCHAR(n)` | `@db.VarChar(n)` | Ahora cuenta caracteres UTF-8, no bytes de la página de códigos 1252 |
| `CHAR(n)` | `CHAR(n)` | `@db.Char(n)` | `dni`, `ruc`, `moneda` |
| `NVARCHAR(MAX)` | `TEXT` | `@db.Text` | `auditoria.detalle`. Sin cambio de contenido |
| `DECIMAL(p,s)` | `NUMERIC(p,s)` | `@db.Decimal(p,s)` | Misma precisión y escala en las 11 tablas. Aritmética exacta; ver `ROUND` abajo |
| `SMALLINT` | `SMALLINT` | `@db.SmallInt` | |
| `TINYINT` | `SMALLINT` | `@db.SmallInt` | `dia_corte` y `dia_pago` ya llevan `CHECK BETWEEN 1 AND 28` |
| `BIT` | `BOOLEAN` | `Boolean` | `permite_fin_mes`, `permite_cuotas`. `CHECK (permite_fin_mes OR permite_cuotas)` |
| `DATE` | `DATE` | `@db.Date` | Prisma lee y escribe medianoche UTC, igual que hoy (`aFechaBd`, `deFechaBd`) |
| `DATETIME2` | `TIMESTAMP(3) WITHOUT TIME ZONE` | `@db.Timestamp(3)` | Hora local de Lima guardada tal cual. Ver 3.1 |
| `TIME` con `DEFAULT '17:00:00'` | `TIME(0) NOT NULL DEFAULT '17:00:00'` | `@db.Time(0)`, `@default(dbgenerated("'17:00:00'::time without time zone"))` | `CHECK (hora_corte = '17:00:00')` igual |
| `DEFAULT CONVERT(DATETIME2, SYSDATETIMEOFFSET() AT TIME ZONE 'SA Pacific Standard Time')` | `DEFAULT (now() AT TIME ZONE 'America/Lima')` | `dbgenerated("(now() AT TIME ZONE 'America/Lima'::text)")` | Da la hora de pared de Lima como `timestamp` (RF, 6.1: zona America/Lima) |
| `CHECK (col LIKE '[0-9]...')` | `CHECK (col ~ '^[0-9]{8}$')` y `{11}` para el RUC | | `dni` y `ruc` |
| `CHECK (... = ROUND(cantidad * precio_lista, 2))` | `CHECK (subtotal = round(cantidad * precio_lista, 2))` | | Las dos funciones redondean `.5` alejándose del cero sobre decimales. Con valores positivos coinciden con `Red(x)` |
| `IN (...)`, `BETWEEN`, `<>` | igual | | Sin cambios |
| Índices únicos filtrados `WHERE x IS NOT NULL` | `CREATE UNIQUE INDEX ... WHERE x IS NOT NULL` | no se declaran en Prisma, como hoy | Se mantienen `ux_cliente_usuario (usuario_id)` y `ux_cliente_codigo (tienda_id, codigo_activacion)` para conservar la regla 1:1 de la Tabla 34 y el nombre. En PostgreSQL un `UNIQUE` normal ya admite varios NULL, pero un `@unique` en Prisma convertiría `usuario.cliente` en 1:1 y cambiaría los tipos del código |
| `UNIQUE (id, tienda_id)` en `cliente` | igual | `@@unique([id, tienda_id])` | Destino de las FK compuestas de `compra` y `listado_pago` (aislamiento multitienda) |
| Collation `Modern_Spanish_CI_AS` (insensible a mayúsculas) | `citext` en 3 columnas | `@db.Citext` | Ver 3.2 |

CHECK y NULL: en las dos bases un CHECK cuyo resultado es NULL se acepta. Ninguna restricción cambia de significado.

### 3.1 Fechas y zona America/Lima

- `fecha_hora` es `timestamp(3) without time zone` y guarda la hora de Lima. Prisma envía el `Date` en UTC y lo lee como UTC: es la convención actual (`aInstanteBd`, `dePartesBd`) y no depende de la zona de la sesión de PostgreSQL ni de la del proceso Node. La prueba S3 (`...17:00:00.900Z`) pasa con precisión de milisegundos.
- La hora de la auditoría sale del reloj de la API; el `DEFAULT` solo cubre inserciones directas y se verifica en `db:verificar` (desfase de hora de Lima menor o igual a 1 minuto, como hoy).
- La zona del servidor ya no la fija el contenedor (`TZ=America/Lima`). Los scripts que lanzan procesos Node (`scripts/db.mjs`, `demo`, e2e) pasan `TZ=America/Lima`; el código no usa `getHours`, `getDate` ni `toLocale*` en `apps/api/src` (revisado: solo `new Date()` en `reloj/reloj.ts`, que se convierte con luxon a la zona explícita).
- El `DEFAULT` de la auditoría y `AT TIME ZONE 'America/Lima'` necesitan la base de zonas horarias de PostgreSQL, que el instalador de Windows incluye. `db:verificar` lo comprueba.

### 3.2 Insensibilidad a mayúsculas (sin esto cambia el comportamiento)

SQL Server compara sin distinguir mayúsculas y PostgreSQL sí. Dónde importa hoy:

| Dónde | Efecto actual | Solución |
|---|---|---|
| `usuario.username` (login `findUnique`, unicidad, alta de dueño, búsqueda) | `ROSA@X` entra y choca con `rosa@x` | `CITEXT`, más `CHECK (char_length(username) <= 120)` para conservar el largo |
| `producto.codigo` (único por tienda, búsqueda) | `p012` choca con `P012` (`CODIGO_DUPLICADO`) | `CITEXT` y `CHECK (char_length(codigo) <= 30)` |
| `cliente.codigo_activacion` (activación `where codigo_activacion = dto.codigo`) | `mdr-7k2q` activa | `CITEXT` y `CHECK (char_length(codigo_activacion) <= 10)` |
| Búsquedas `contains` en `clientes.ts:168`, `productos.ts:101`, `plataforma.service.ts:66` y `:225` | Insensibles a mayúsculas | Agregar `mode: 'insensitive'` en cada `contains` (Prisma usa `ILIKE`). Sigue siendo sensible a tildes, como `_AS` |

`CREATE EXTENSION IF NOT EXISTS citext` lo ejecuta `vecinopay_owner` (extensión de confianza desde PostgreSQL 13; no requiere superusuario). `giro` y los demás textos quedan como `VARCHAR`: el gráfico de A02 agrupa por `giro` y los datos vienen de A03 con mayúscula consistente; es un riesgo bajo, anotado en la sección 11.

## 5. Roles, privilegios y `db/` (puntos 2 y 8)

### 5.1 Roles

| Rol | Atributos | Para qué |
|---|---|---|
| `postgres` | superusuario existente | Solo `npm run db:roles`, una vez. Su contraseña no se guarda en ningún archivo ni en `.env` |

### 5.2 Privilegios del rol de la API (equivalen a `03_usuario_app.sql` de hoy)

- `SELECT, INSERT, UPDATE` en `usuario`, `tienda`, `producto`, `cliente`, `compra`, `cuota`, `listado_pago`.
- `SELECT, INSERT` en `compra_detalle`, `listado_item`, `pago`, `auditoria`.
- Ningún `DELETE`, ningún `TRUNCATE`, ningún `REFERENCES` ni `TRIGGER`, en ninguna tabla. PostgreSQL no tiene `DENY`: basta con no conceder, porque los privilegios solo suman y `PUBLIC` no recibe nada. No es dueño de las tablas, así que `ALTER TABLE`, `DROP`, `DISABLE TRIGGER` y `TRUNCATE` fallan con `permission denied` o `must be owner`.
- `REVOKE ALL ON DATABASE <db> FROM PUBLIC; GRANT CONNECT ON DATABASE <db> TO vecinopay_app;` y `REVOKE CREATE ON SCHEMA public FROM PUBLIC; GRANT USAGE ON SCHEMA public TO vecinopay_app;`. El `postgres` de pgAdmin sigue entrando por ser superusuario.
- No hace falta `GRANT` sobre secuencias (columnas `IDENTITY`).

## 6. Prisma y capa de datos (punto 3)

### 6.1 `apps/api/prisma/schema.prisma`

- `provider = "postgresql"`; `url = env("DATABASE_URL")`; se mantiene `prisma-client-js` y la versión exacta 6.19.3. Hay que ejecutar `prisma generate` (el `prebuild` ya lo hace).
- Tipos: `@db.TinyInt` a `@db.SmallInt`; `@db.NVarChar(Max)` a `@db.Text`; `@db.Time` a `@db.Time(0)`; `fecha_hora` de `compra` a `@db.Timestamp(3)` explícito, y `auditoria.fecha_hora` igual; `@default(dbgenerated(...))` de `hora_corte` y de `auditoria.fecha_hora` con las expresiones de la sección 3.
- `username`, `producto.codigo` y `cliente.codigo_activacion` pasan a `@db.Citext`. Si Prisma 6.19.3 exigiera `previewFeatures = ["postgresqlExtensions"]` y `extensions = [citext]`, se agregan; lo confirma la prueba de concepto del paso 0.
- `map:` de claves, únicos y defaults en minúscula para coincidir con la base. `BigInt`, `Decimal`, `Boolean`, `Char`, `VarChar` y las relaciones no cambian, así que `ambito-tienda.ts` y los demás servicios compilan igual.
- Bajo ningún concepto se usa `prisma migrate` ni `db push`: el esquema lo manda `db/init/01_esquema.sql`. Se puede validar con `prisma db pull --print` contra la base de prueba y revisar a mano que no haya diferencias.

### 6.2 `apps/api/src/bd/bd.service.ts`: bloqueos

| Método | Sentencia actual | Sentencia nueva |
|---|---|---|
| `bloquearTienda` | `SELECT id FROM dbo.tienda WITH (UPDLOCK, ROWLOCK) WHERE id = ${tiendaId}` | `SELECT id FROM tienda WHERE id = ${tiendaId} FOR NO KEY UPDATE` |
| `bloquearCliente` | `... dbo.cliente WITH (UPDLOCK, ROWLOCK) WHERE id = ${id} AND tienda_id = ${tiendaId}` | `SELECT id FROM cliente WHERE id = ${id} AND tienda_id = ${tiendaId} FOR NO KEY UPDATE` |
| `bloquearListado` | `... dbo.listado_pago WITH (UPDLOCK, ROWLOCK) WHERE id = ${id} AND tienda_id = ${tiendaId}` | `SELECT id FROM listado_pago WHERE id = ${id} AND tienda_id = ${tiendaId} FOR NO KEY UPDATE` |
| `bloquearClienteEn` (activación, sin tienda) | `... dbo.cliente WITH (UPDLOCK, ROWLOCK) WHERE id = ${clienteId}` | `SELECT id FROM cliente WHERE id = ${clienteId} FOR NO KEY UPDATE` |

Por qué `FOR NO KEY UPDATE` y no `FOR UPDATE` ni `pg_advisory_xact_lock`:

- `UPDLOCK` no bloquea a lectores ni a las comprobaciones de clave foránea (el bloqueo de actualización es compatible con el compartido). En PostgreSQL un `INSERT` en una tabla hija toma `FOR KEY SHARE` sobre la fila padre. `FOR UPDATE` choca con `FOR KEY SHARE`: bloquearía el alta de `producto`, `cliente`, `compra` o `auditoria` de la misma tienda hechos por transacciones que no piden el bloqueo (por ejemplo, el LOGIN auditado con `tienda_id`). `FOR NO KEY UPDATE` choca con los demás bloqueos de este mismo tipo y con los `UPDATE`, pero no con `FOR KEY SHARE`: es el equivalente fiel.
- Un advisory lock obligaría a inventar una clave por entidad y no protegería contra un `UPDATE` directo. Las filas ya existen y son lo que se quiere serializar.
- Aislamiento: Prisma usa `READ COMMITTED` en PostgreSQL, igual que en SQL Server. Tras obtener el bloqueo, la siguiente sentencia ve los cambios ya confirmados (cada sentencia toma un snapshot nuevo). La regla se mantiene: primero `bloquearTienda`, luego `bloquearCliente`, luego `bloquearListado`, y recién después leer saldos o generar el ticket (`compras.ts:244-245,287`, `cortes.ts:121-122`, `listados.ts:271-272`). El único respaldo de duplicados sigue siendo `uq_compra_tienda_ticket`.
- No se cambia el nivel de aislamiento a `SERIALIZABLE`.
- Cambia el nombre de la tabla (sin `dbo.`). Los bloqueos siguen siendo las únicas consultas crudas de `src/`; la regla ESLint de `$queryRaw` y `$executeRaw` se conserva y la excepción de `bd/` también.

### 6.3 Errores, reintento y transacciones abortadas

- `conReintento`: se mantiene `P2034` y `message.includes('deadlock')`; se agrega `message.includes('could not serialize')`. PostgreSQL señala interbloqueo con `40P01` y serialización con `40001` (Prisma lo traduce a `P2034` en sentencias del modelo y a `P2010` con el texto del servidor en consultas crudas; por eso se mira el mensaje). Con el orden fijo de bloqueos no deberían ocurrir.
- `restriccionUnica` (`errores-bd.ts`). Hoy devuelve `dbo.usuario`, `dbo.producto`... y los llamadores usan `.includes('usuario')`, `.includes('producto')`, `.includes('tienda')` (`auth.service.ts:176`, `productos.ts:89`, `plataforma.service.ts:41-43,261`). En PostgreSQL Prisma informa en `meta.target` las columnas (`['username']`) o el nombre del índice, no la tabla, y esos `includes` dejarían de acertar. Contrato nuevo, manteniendo la firma `string | null` y devolviendo siempre el nombre lógico de la tabla:

  | `meta.target` (columnas o nombre del índice) | Devuelve |
  |---|---|
  | `username` / `uq_usuario_username` | `usuario` |
  | `ruc` / `uq_tienda_ruc` | `tienda` |
  | `tienda_id,codigo` / `uq_producto_tienda_codigo` | `producto` |
  | `tienda_id,dni`, `usuario_id`, `tienda_id,codigo_activacion` y sus nombres | `cliente` |
  | `tienda_id,ticket` | `compra` |
  | `cliente_id,fecha_corte`, `tienda_id,numero` | `listado_pago` |
  | `listado_id` (pago) / `uq_pago_listado` | `pago` |
  | `compra_id,numero` | `cuota` |
  | `listado_id,orden` | `listado_item` |
  | otro código `P2002` no mapeado | el texto original (nunca `null`, para que `clientes.ts:266` y `listados.ts:260` sigan reintentando o respondiendo 409) |

  Un test unitario fabrica `PrismaClientKnownRequestError` con las dos formas de `target`; una prueba de integración provoca cada duplicado real y comprueba el mapeo. La forma exacta de `meta.target` la fija el paso 0.
- Transacción abortada: a diferencia de SQL Server, tras un error SQL dentro de una transacción de PostgreSQL ninguna sentencia más funciona hasta el rollback. Revisado: todo `try/catch` de `src/` envuelve a `transaccionEnTienda` o `transaccionGlobal` desde afuera (`clientes.ts:219`, `plataforma.service.ts:77,131,244`, `cortes.ts:79,107`, `productos.ts:110,137`, `listados.ts:258`, `auth.service.ts:174`), nunca dentro del callback. Se deja como regla del diseño y se cubre con una prueba de integración (duplicar un DNI dentro de una alta rechaza con 409 y la siguiente operación funciona).
- Violación de CHECK, FK y triggers: Prisma devuelve un error con el texto del servidor (`violates check constraint "ck_cuota_monto"`, `... foreign key constraint "fk_compra_cliente"`, o el mensaje en español del trigger). Los nombres en minúscula son lo único que cambia respecto de los textos de SQL Server que usan las pruebas.
- Tiempo de bloqueo: `lock_timeout = '12s'` por rol (5.1). Vence con SQLSTATE `55P03`; la API responde 500 como cualquier error de BD no previsto, y es un caso patológico (dos operaciones de la misma tienda en más de 12 s).

### 6.4 Consultas con orden no determinista (cifras y pantallas)

PostgreSQL no garantiza el orden de las filas empatadas ni respeta el orden físico después de un `UPDATE`. Hay `orderBy` con una sola clave que puede empatar (por ejemplo `fecha_pago asc` entre las cinco compras del 26/09, `fecha_corte desc`, `fecha asc`: `mi.ts:50,55,59,147,160,199,243`, `listados.ts:94`, `plataforma.service.ts`, `compras.ts:348` ya lleva `id`). Cambio: agregar `{ id: 'asc' }` (o `desc`, el sentido de la clave principal) como desempate en todo `orderBy` cuya clave no sea única. No cambia ningún valor, solo vuelve determinista lo que SQL Server devolvía por casualidad en el orden de inserción. Se revisa con `Grep orderBy` (paso 5).

## 12. Riesgos y supuestos

| Riesgo | Efecto | Mitigación |
|---|---|---|
| Orden de filas empatadas distinto | Lista de compras, cuotas o cobros con otro orden; una cifra no cambia pero sí la pantalla o una aserción | Desempate por `id` (6.4) |
| Comparación sensible a mayúsculas | Login, activación y duplicados se comportan distinto | `citext` y `mode: 'insensitive'` (3.2) |
| `FOR UPDATE` en lugar de `FOR NO KEY UPDATE` | Bloqueos inesperados en altas de la misma tienda | Contrato fijo en 6.2 y prueba S8 |
| Transacción abortada tras un error | Una operación que antes seguía ahora falla en cadena | Ningún `catch` dentro de un callback transaccional; prueba nueva |
| `meta.target` de `P2002` distinto del esperado | Un 409 se convierte en 500 (`USUARIO_DUPLICADO`, `RUC_DUPLICADO`, `CODIGO_DUPLICADO`, `LISTADO_YA_PAGADO`) | Mapa explícito, test unitario y prueba real por cada duplicado; el paso 0 fija la forma |
| `ROUND` de decimales | Una cifra de céntimos cambia | Las dos bases redondean `.5` alejándose del cero sobre `NUMERIC` y todos los montos son positivos; la verificación 52 y las pruebas de motor (el motor usa `decimal.js`, no la base) lo cubren. `CK_detalle_subtotal` y las semillas lo comprueban |
| Fecha y hora con corrimiento | `fecha_corte` o `fecha_hora` un día o 5 horas distinto | `timestamp` sin zona y `date`; pruebas S3 y S4, `db:verificar` y e2e |
| Orden alfabético distinto (`giro`, `nombre`) | Solo apariencia | Base ICU `es-PE`; se acepta |
| Agrupar `giro` sin `citext` | Un giro con otra mayúscula se cuenta aparte | Los datos de A03 y las semillas son consistentes; se acepta |
| Prisma 6.19.3 sobre Node 26 en Windows | El cliente no arranca | Paso 0; la alternativa es instalar Node 22 solo para el repositorio (el motor de Prisma es binario de N-API), sin cambiar el diseño |
| El rol `vecinopay_owner` no logra `CREATE EXTENSION citext` | El esquema no se aplica | `citext` es de confianza desde PostgreSQL 13; si el servidor no la trae instalada (`postgresql-contrib` va incluido en el instalador de Windows) se avisa en `db:estado` |
| Locale del clúster en Windows (`Spanish_Peru.1252`) con base UTF8 | `CREATE DATABASE` rechaza la combinación o `ILIKE` no distingue ñ | Base con `LOCALE_PROVIDER icu`; chequeo de plataforma `'Doña' ILIKE 'doña'`; `db:estado` muestra los datos |
| Contraseñas en la URL | Un `#` o `@` rompe la URL | Contraseñas de ejemplo sin caracteres especiales; los scripts codifican; `configuracion.ts` decodifica |
| `lock_timeout` de 12 s | Un bloqueo largo falla con 500 | Es menor que el tiempo máximo de Prisma; situación patológica |
| Procesos huérfanos del e2e en Windows | Puertos 13000 o 18080 ocupados en la siguiente corrida | PID en archivo, `taskkill /T /F` al inicio de `global-setup` si el PID existe, y mensaje claro si el puerto está en uso |
| Cargar `.env` de desarrollo en el e2e | El e2e usaría la base de desarrollo | El hijo recibe `DATABASE_URL` explícita (`cargarEnv` no pisa variables ya definidas); `entorno.ts` falla si `E2E_DB_NAME == DB_NAME` |
| Datos previos en SQL Server (Docker) | Se pierden | Se confirma que solo eran semillas (decisión 5) |

Supuestos: el servicio `postgresql-x64-17` está activo y escucha en `127.0.0.1:5432` con autenticación por contraseña (`scram-sha-256`); `psql.exe` está en `C:\Program Files\PostgreSQL\17\bin`; el usuario conoce la contraseña de `postgres`; la PC tiene internet para que `prisma generate` descargue su motor (como con SQL Server). Ningún RF cambia. Ninguna cifra de 6.3 ni 6.4 depende del motor de base de datos: el motor financiero es `packages/finance` con `decimal.js`, y la base solo guarda y suma importes ya redondeados con `Red(x)`.

## 13. Decisiones que necesito del usuario

1. **[ESCALAR] Contraseña del superusuario `postgres`.** No la invento ni la leo de ningún archivo. Se escribe solo cuando `npm run db:roles` la pida (o con `$env:PGPASSWORD` en esa terminal). Alternativa: ejecutar `db/roles.sql` en la ventana de consultas de pgAdmin como `postgres`, reemplazando las dos contraseñas a mano.
2. **Contraseñas de `vecinopay_owner` y `vecinopay_app`.** Usar las de `.env.example` (solo desarrollo local) o elegir otras. Deben ir sin `# @ : / ? %`.
3. **Confirmar puerto y ruta.** `127.0.0.1:5432` y `C:\Program Files\PostgreSQL\17\bin\psql.exe`. En pgAdmin: Propiedades del servidor, o `SHOW port;`.
4. **[ESCALAR] Permiso para borrar** los 8 archivos de la sección 10.1 (recuperables desde Git).
5. **Datos del SQL Server anterior.** Confirmar que solo contenía semillas y que no hace falta migrar nada. La base nueva se crea desde cero con `db:crear`.
6. **Configuración regional de la base.** Usar ICU `es-PE` si la instalación la trae (recomendado); si no, la configuración por defecto del clúster.
7. **`citext`** en `username`, `producto.codigo` y `cliente.codigo_activacion` para conservar el comportamiento insensible a mayúsculas del SQL Server original.
8. **Servidor web de la demo.** `vite preview` con proxy (sin dependencias) en lugar de un servidor aparte. Es lo que propone este diseño.
9. **Quién corrige el Word.** Sección 8 (tipos de las Tablas 27 y 33), líneas 375, 444, 4428 y 5109 y las Figuras 48 y 49 del Anexo 4 (script T-SQL). Ya figura como pendiente del grupo en `docs/escalaciones.md`.
10. **Exposición en red.** La web ya no escucha en todas las interfaces, solo en `127.0.0.1`. Indicar si alguna vez se mostrará la demo desde otro equipo de la red local.
